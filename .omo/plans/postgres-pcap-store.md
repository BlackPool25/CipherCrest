# postgres-pcap-store - Work Plan

## TL;DR (For humans)

**What you'll get:** A Postgres Docker container that becomes the single source of truth for every page — Families, Lab, Live, Dashboard and Reports — seeded automatically on `git clone → docker compose up` with 60 families' pcaps and model info, fixing the "one run resets others" bug and letting dashboard graphs, triage and protocol analytics query real DB rows instead of hardcoded JSON.

**Why this approach:** Startup-idempotent seeding (FastAPI lifespan, not init-only) plus JSONB + BYTEA + derived `not_run` status via EXISTS keeps clone UX simple while guaranteeing history-preserved reruns, always-SELECT reads and streamed BYTEA avoid the three critical data-loss/OOM/race traps flagged in brutal reviews.

**What it will NOT do:** No S3/minio spill for pcaps (pure BYTEA), no SQLite auto-migration on fresh clones (optional one-shot script only), no UI theme restyle (TOK frozen, extend-only).

**Effort:** Large (3–4 days, schema + seed + API + frontend wiring + matviews)
**Risk:** Medium — driver: BYTEA TOAST memory + history MAX(version)+1 race + matview CONCURRENTLY unique-index requirement all mitigated by streaming, FOR UPDATE tx and debounced NOTIFY.
**Decisions to sanity-check:** BYTEA pure vs hybrid, 6 base tables + 2 matviews vs 7, derived not_run vs enum-only, init-only vs startup-idempotent seed, matview NOTIFY 5s debounce.

UI styling flow: All frontend todos must preserve Donezo SaaS edge-to-edge widescreen, 540px slide-over drawer + backdrop, TOK palette (#1F7A4D/#E7F5EC/#F6F8F7), Inter/JetBrains Mono, Recharts capsule/gutter patterns, header filter toolbar layout — data wiring must flow styling, not restyle it; worker must visual-QA screenshots diff <2% pixels beyond new status badge/matrix rows.
